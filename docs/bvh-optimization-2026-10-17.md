## 1. 结论与适用范围

本轮建立了可复现的 WebGPU 最近命中求交基准，最终同一轮比较 **16 个条目：15 个修复后的配置（含基线），以及一个保留缺陷的 `original` 负对照**。**可用适配器是 SwiftShader 软件实现，没有物理 GPU 性能结果。** 毫秒数来自该软件适配器的 WebGPU compute pass 时间戳，不能外推为用户显卡速度、完整渲染帧率或物理镜头追迹速度。

本次软件运行中，修复后的配置里 **`branchless-slabs` 的中位耗时最低**：别墅 475.038 → 448.165 ms，降低 **5.7%**；植被 520.249 → 484.529 ms，降低 **6.9%**。`leaf8` 分别降低 0.9% / 5.8%，其中别墅收益较小、波动明显。

**这些收益都相对于修复后的 `baseline`。** 修复前 `original` 为 430.647 / 467.887 ms；`branchless-slabs` 仍比它多用 **4.1% / 3.6%** 时间。因此，这次软件测量没有展示既通过边界正确性检查、又快于原始 main 实现的方案。实际交付是正确性修复、可重现的比较工具，以及下一步的候选方向。

生产代码只纳入平行轴正确性修复。叶大小、算术改写、栈容量与 `branchless-slabs` 均留在实验文件中，供硬件对照。没有用有漏交的实现作为可部署的速度优化。

完整场景的 634,040 个节点中，527,983 个属于 TLAS。两个完整场景视角的 TLAS 包围盒测试分别占全部 AABB 测试的 60.3% 和 68.9%。 **下一阶段优先验证 TLAS 的宽节点与保守量化布局。** 节点占比和事件次数占比都不是耗时占比，这一优先级仍是需要硬件测量验证的工程推断。[完整原始数据](benchmarks/bvh-2026-10-17-final.json)

## 2. 当前实现已经做了哪些优化

本项目当前使用两级软件 BVH：TLAS 组织实例，BLAS 组织共享几何中的三角形。构建器采用二叉树和 16 桶 SAH，TLAS 叶子含一个实例，BLAS 默认叶目标为 4；遍历根据两个子节点的 `tNear` 先近后远，并用最近命中的 `tMax` 剪枝。实例变换后在局部空间继续求交；三角形求交已有主轴变换和带补偿的乘积差计算。相关实现见 [BVH 构建器](../src/scene/bvh-builder.js) 与 [场景求交 shader](../src/rendering/scene-intersector.wgsl)。

因此，单纯建议“改成 SAH”“先遍历近节点”或“找到近交点后缩短射线”不会给当前实现增加这些能力。当前渲染使用直接光照和阴影贴图，也没有可直接受益于 any-hit 专用遍历的次级遮挡射线调用。

### HUD 中的 BVH 占比如何解读

[工作量模型](../src/rendering/work-model.js) 把运行时事件计数乘以人工设定的算术权重，再汇总到 BVH 等类别。例如包围盒、三角形、实例事件的权重分别为 26、50、45。这个 HUD 是工作量估计，**没有测出 GPU 在 BVH 上消耗了多少毫秒**；内存访问、动态索引、寄存器压力、编译器消除和线程执行差异都不能由这些权重完整表达。

本次另行记录了实际包围盒、三角形、实例测试次数，用于解释算法行为；性能判断则用独立的时间戳测量。二者不可互相替代。

## 3. 首先修复平行轴上的边界漏交

原始 `sceneBox` 对零方向使用安全倒数，然后统一做 slab 测试。当某轴方向为零、原点恰好位于包围盒该轴的上边界时，`(hi - origin) * inverseDirection` 会得到 0，把该轴的离开时间错误地限制为 0。射线可能沿其他轴在正时间进入几何，却被包围盒提前排除。

修复按真实的 `direction == 0` 判断平行轴：原点位于闭区间 `[lo, hi]` 内时，该轴不限制射线区间；在区间外时直接拒绝。这里不能把极小的非零方向当成零，否则会改变贴边射线的结果。CPU 打包树参考遍历同步处理零方向，避免相应的边界与 `0 × Infinity` 问题。

[新增回归测试](../tests/scene-bvh.test.mjs) 含 10 个明确用例：上角、上边界及负零方向，下角与非单位方向，刚好位于包围盒之外，以及 `±1e-12` 的非零方向从两侧进入或离开边界。CPU 测试与 f64 暴力参考比较；另有第 4 节所述 GPU 边界工作负载。新增的 10 个用例不等于全部 GPU 边界覆盖。

- `baseline`：原始提交加本节正确性修复，作为全部有效优化的共同基线。
- `original`：实验工具恢复修复前的 slab 实现与调用，用作负对照；它不属于默认的 14 方案。

原始负对照在边界负载上确实失败，而修复版通过。修复的性能成本也被单独测量，见第 8 节；修复与优化的分母始终明确区分。

## 4. 测试方法

### 环境与统计

使用 Chromium **134.0.6998.35**，WebGPU 适配器返回 `vendor: google`、`architecture: swiftshader`、`isFallbackAdapter: true`，支持 `timestamp-query`。从 `/tmp/lens-bvh-singleworker` 启动，`SwiftShader.ini` 配置为：

```ini
[Processor]
ThreadCount=1
AffinityMask=0x1
AffinityPolicy=one
```

同时用 `taskset -c 0` 启动。JSON 记录 INI 内容及路径、父进程 CPU affinity、CPU quota / cpuset、浏览器版本与启动参数。**没有独立观测 GPU 子进程实际工作线程数量**，所以本文称其为“配置为单工作线程 / CPU0 的软件复测”。

每个负载固定 **8,192 条 f32 射线**，每个条目 **9 轮**，初始预热 2 次，每个计时样本前再执行一次当前方案、不计时的预热 dispatch。计时范围是一遍独立最近命中 compute pass；编译、场景构建、预热和结果回读不计入时间戳。另存提交至完成的 wall time，与时间戳使用不同字段。

每轮轮转方案顺序，隔轮反向，并保存逐轮基线比值。这是 **interleaved 交错测量，不是完全平衡的顺序设计**；9 轮不足以覆盖 16 个条目的所有位置。逐轮配对也不是立即相邻的 A/B 样本。数据 checkpoint 发生在工作负载切换或全部完成时，没有逐 dispatch 或逐轮写文件。

主表显示 9 个样本的中位数与 P25–P75 区间。四分位区间按排序样本的对应位置计算，是离散度描述，**不是置信区间或显著性检验**。“耗时降低”使用 `100 × (1 - 方案中位数 / baseline 中位数)`，正数更快、负数更慢。原始 JSON 保留全部时间样本、配对加速比、计数和校验结果。

### 正确性与独立计数

事件计数和栈峰值在独立、不计时的插桩 shader 中采集。也单独 dispatch 并回读**未插桩的计时 shader**做校验，避免遗漏两种编译结果的差异。所有条目在全部 8,192 条射线上与修复基线比较；`diagnostic`、`edges` 还分别与前 2,048 条 f64 暴力参考比较。f64 参考使用已转换为 f32 的输入，确保比较同一条射线。

检查覆盖命中状态、遍历错误、实例 / 三角形身份、朝向、距离、重心坐标和非有限值。相对距离阈值为 `2e-5`，重心阈值为 `1e-3`；同一实例上确有共享拓扑的边 / 顶点，允许 `1e-4` 范围内等距身份平局，不接受任意相近交点作为身份匹配。

**15 个修复后的配置（含基线）在 4 个工作负载上共 60 / 60 项通过**适用检查。`original` 仅在 `edges` 失败，其余三个工作负载通过；64 个组合中这一项已知失败使原始报告顶层 `passed` 保持 `false`，没有掩盖负对照。 完整场景没有逐射线 f64 暴力真值；基线等价检查不能证明尚未覆盖的全场景正确性。[基准工具](../tests/bvh-benchmark.js)、[工作负载与参考生成](../tests/bvh-workloads.js)

## 5. 默认 14 个方案与两个补充对照

| 方案 | 相对修复基线的变化 |
| --- | --- |
| `baseline` | 修复后的生产 shader；BLAS 叶目标 4；64 项栈 |
| `static-axis` | 把三角形主轴排列中的动态分量索引改为固定 swizzle / select，保留边函数算术顺序 |
| `reciprocal` | 三角形距离与重心坐标共用 `1 / det`；极小 `det` 保留原除法路径，避免先求倒数溢出 |
| `tiny-leaf` | BLAS 根本身为叶子时跳过根 AABB，直接测试三角形；保留射线区间与其余正确性检查 |
| `stack-size` | 按 `TLAS 最大深度 + BLAS 最大深度` 设置栈，本次完整场景为 54 |
| `stack-proved` | 按每个实际 TLAS 叶子及其引用 BLAS 的联合路径证明容量，本次完整场景为 34 |
| `parallel-fast` | 所有方向分量非零时走原 slab 算术；含零分量时走修复路径 |
| `combined` | `static-axis + reciprocal + tiny-leaf + stack-size`；本次场景栈 54 |
| `fast-combined` | 上述组合加 `parallel-fast`，并用联合路径证明；本次场景栈 34 |
| `leaf2` | 仅将 BLAS 叶目标设为 2，复用 TLAS |
| `leaf8` | 仅将 BLAS 叶目标设为 8，复用 TLAS |
| `leaf8+tiny-leaf` | 叶目标 8，加根叶直接测试 |
| `leaf8+combined` | 叶目标 8，加 `combined`；本次场景栈 52 |
| `leaf8+fast-combined` | 叶目标 8，加 `fast-combined`；本次场景栈 33 |

最终完整运行另外增加两项：`original` 恢复修复前的 slab 代码，用来检验边界回归；`branchless-slabs` 在源码中用 `select` 统一选择平行轴的最终近 / 远端点，保留非平行轴原算术。它仍按真实 `d == 0` 判断，没有增加方向 epsilon；对区间外的平行轴使用会被既有哨兵 / 区间检查拒绝的端点。`select` 作用在原 `min/max` 之后，避免把空区间交换成有效区间。这个源码改写没有保证机器代码一定无分支。

“叶目标”不是严格最大值。生产 SAH 在一定范围内可以选择更大的叶子；本次 `leaf2`、`leaf8` 的实际最大 BLAS 叶分别为 4 和 16 个三角形。重建与 shader 变体使用独立的 [构建实验模块](../tests/bvh-build-variants.js)、[shader 实验模块](../tests/bvh-variants.js)，生产构建参数未改变。

### 64 → 34 的依据是结构证明

简单上界把全场景最深 TLAS 路径 30 与最深 BLAS 路径 24 相加，得到 54。两个最深路径未必能在同一实例上同时出现；联合证明验证实际打包树、叶引用与三角形范围，取每个实例对应的 `TLAS 叶深度 + 该实例 BLAS 深度` 的最大值，得到 34。

这是针对本次二叉树打包结构的保守容量证明，**不是把已观测的栈峰值当作容量**。本次两视角实际峰值分别为 17 和 15，仍不能据此把栈容量设为观测峰值。证明也不是所有场景的固定常数；几何或树布局变化时必须重算，宽 BVH 更不能直接沿用二叉树证明。缩小数组是否减少硬件寄存器溢出或改善占用率，还需要目标 GPU 的结果。

更早的临时环境曾出现候选排名随运行配置变化；其逐轮轨迹已丢失，本文只把这一观察作为复测动机，没有将旧数据用于表格或跨环境比较。

`leaf8` 把 BLAS 节点减少 **44.60%**，TLAS 没有变化，总节点只减少 **7.46%**。实例数与三角形几何数据也没有减少。叶大小实验复用了 TLAS，部分后续运行还复用了 BLAS；构建计时包含这些不同缓存状态，**不能据此横向排名构建速度**。

默认叶大小下，`tiny-leaf` 省下的 AABB 次数很少。`leaf8` 使 200,442 个实例（75.93%）引用根为叶子的 BLAS，但这只是实例结构比例。再跳过这些根 AABB 时，三角形数从 25.163 / 30.292 上升到 31.670 / 39.992，分别比 `leaf8` 多 25.86% / 32.02%，时间收益消失。

## 8. 正确性修复与负对照

`original` 在新边界集合上有 **1,707 / 8,192** 条状态不一致，与前 2,048 条 f64 参考比较有 **427 / 2,048** 条不一致；插桩和未插桩 shader 结果相同。修复基线和 `branchless-slabs` 都通过。该比例只描述特意构造的边界测试集合。

| 实现 | 边界集合命中数 | 对修复基线的状态失配 | 对 f64 参考的状态失配 |
| --- | ---: | ---: | ---: |
| `baseline` | 6,142 | 0 / 8,192 | 0 / 2,048 |
| `original` | 4,435 | 1,707 / 8,192 | 427 / 2,048 |
| `branchless-slabs` | 6,142 | 0 / 8,192 | 0 / 2,048 |

因此原始 JSON 顶层 `passed: false` 是保留已知有缺陷实现的预期结果。没有改写这个字段；应同时查看每个候选的 `passed` 以及 `original` 的具体失败项。

同一次运行、相同两组相机射线中，以原始实现时间为分母，修复基线分别增加 **10.3% / 11.2%** 时间。`branchless-slabs` 把修复基线的耗时降低 5.7% / 6.9%，但相对原始实现仍增加 **4.1% / 3.6%**。这几个百分比使用不同分母，不能互换。

本轮保留 `branchless-slabs` 为实验选项，没有将它设为生产默认；目标硬件的性能仍待测量。 原始实现即使在两个相机样本上与修复基线命中一致，也不能消除边界集合中已证实的缺陷。修复成本和优化收益必须同时说明，主表百分比统一使用修复基线。[原始数据及全部校验](benchmarks/bvh-2026-10-17-final.json)

## 9. 文献核对与下一步的三个优先方向

### 1. 优先做 TLAS 的 BVH4，对照后再决定是否推进 BVH8

当前树的结构和实测 AABB 次数都表明 TLAS 是值得优先处理的层级。建议先保留 BLAS，单独把二叉 TLAS 折叠成 4 路节点，再测是否值得增加到 8 路；这样能把层数、节点读取和子节点测试成本的变化定位清楚。

Ylitie、Karras、Laine 的 *Efficient Incoherent Ray Traversal on GPUs Through Compressed Wide BVHs* 提供了宽节点、紧凑编码、遍历排序和压缩栈的完整设计。它说明这些部分需要协同设计，不能把“更宽”等同于“更快”。论文使用的硬件、执行模型、光线分布与本项目不同，本文不把论文加速比用作项目预期值。[作者机构论文页](https://research.nvidia.com/publication/2017-07_efficient-incoherent-ray-traversal-gpus-through-compressed-wide-bvhs)、[论文 PDF](https://research.nvidia.com/sites/default/files/publications/ylitie2017hpg-paper.pdf)

需要一起验证的约束包括：每次测试更多子 AABB 的代价、近远排序代价、更多临时状态；BVH4 / BVH8 每层可能留下 3 / 7 个待访问兄弟，树更浅不自动意味着栈更小，必须重新证明容量或采用分组位掩码栈。此外，论文的三角形叶编码不能直接照搬到 TLAS 实例叶，仍需保留实例身份、BLAS 根、局部变换和世界射线恢复语义。

**待验证的推断：** TLAS 宽化可能比继续调整 BLAS 叶大小更有收益。当前证据只支持优先实验，没有测出宽 TLAS 的速度。

### 2. 对宽 TLAS 实验保守量化和布局压缩，先验证解码后的包含关系

节点读取量是另一个可测试方向。上述 CWBVH 论文使用节点局部网格和量化子包围盒；对本项目，更合适的实验是保留现有世界空间保守扩张，对子边界做向外量化，并验证实际 f32 解码值仍包含未量化边界，而非直接把世界坐标换成低精度格式。

要覆盖大坐标、极薄叶片、零跨度轴，以及网格过粗造成的边界膨胀。量化后的 AABB 若更松，可能增加 TLAS 子节点命中、实例进入和 BLAS 工作，抵消节省的字节；所以需要同时报告内存、测试次数和计时。

Ize 的 *Robust BVH Ray Traversal* 分析了浮点 slab 测试的保守性；作者还发布了对原文一种 FMA 分析的修订。其意义是任何压缩和算术改写都需要自己的误差论证与边界测试，而非把现有三角形补偿乘积差删除，或笼统认定 FMA 不可用。[论文与修订版 PDF](https://jcgt.org/published/0002/02/02/paper.pdf)、[作者修订说明](https://www.sci.utah.edu/~thiago/)

**待验证的推断：** 压缩 TLAS 可能改善目标 GPU 的读取成本；本轮没有带宽或缓存测量，也没有量化 TLAS 实现。

### 3. 用真实物理镜头出射射线和硬件时间戳校准后续结构选择

当前 `leaf8` 结果已经说明，减少一种事件可能增加另一种事件。Aila、Karras、Laine 的 *On Quality Metrics of Bounding Volume Hierarchies* 讨论了 SAH 以外的重叠、叶工作量差异与实际遍历表现；不能只依靠 SAH 分数或总节点数选择结构。[论文 PDF](https://users.aalto.fi/~ailat1/publications/aila2013hpg_paper.pdf)

下一轮应在用户的目标 GPU 上保存实际镜头出射射线，复用当前固定输入、计数与未插桩验证流程。至少同时比较 TLAS / BLAS 的 AABB 次数、实例进入、三角形数、较长遍历射线与 compute pass 时间，再测同一相机的完整渲染。静态植被的空间分块也值得作为独立实验：263,992 个实例对应 527,983 个 TLAS 节点，分组可能减少顶层叶子，但应保留共享几何复用。本场景只有 175,654 个唯一三角形，按实例展开却有 3,471,208 个；把共享几何全部展开会增加三角形存储。较少的 TLAS 叶还可能伴随更重叠的组包围盒、更多局部工作和身份映射成本，分组的实际耗时尚未测量。

**待验证的推断：** 真实光学出射方向、光圈与遮挡分布可能改变本轮候选的排序。现有几何射线能建立可复现对照，但尚未证明相同改动能降低完整渲染耗时。

## 10. 复现与交付

### 浏览器：显式要求硬件适配器

在项目目录安装依赖并启动开发服务器：

```sh
git submodule update --init --recursive
npm ci
npm run dev
```

在支持 WebGPU 的浏览器中打开 Vite 提示的地址，并使用路径：

```text
/tests/bvh-benchmark.html?hardware=1&rays=8192&rounds=9
```

`hardware=1` 会拒绝被识别为 SwiftShader / 软件回退的适配器；页面显示 JSON 并可下载。没有 `timestamp-query` 时工具保留正确性和 wall time，`gpuMs` 与对应加速比为 `null`，不会把 wall time 冒充 GPU 时间。

### CLI：可记录浏览器与启动环境

[CLI 驱动](../scripts/benchmark-bvh.mjs) 本次使用 **Playwright 1.51.1** 和 **Chromium 134.0.6998.35**。以下命令固定相同的 Playwright 版本；也可通过 `PLAYWRIGHT_MODULE` 与 `CHROMIUM_PATH` 指向已有安装。更换浏览器或适配器后，结果只适用于对应环境。

```sh
npm install --no-save --package-lock=false playwright@1.51.1
npx playwright install chromium
node scripts/benchmark-bvh.mjs --rays 8192 --rounds 9 --out artifacts/bvh-hardware.json
```

CLI 默认要求硬件适配器；软件测试需显式选择：

```sh
node scripts/benchmark-bvh.mjs --software --rays 8192 --rounds 9 --out artifacts/bvh-software.json
```

支持 `--workloads`、`--variants`、`--warmups`、`--label`、`--headed` 与 `--chromium`。省略 `--variants` 时使用默认 14 项；要完整复现本报告含负对照的 16 项，使用：

```sh
node scripts/benchmark-bvh.mjs --software --variants baseline,original,static-axis,reciprocal,tiny-leaf,stack-size,stack-proved,parallel-fast,branchless-slabs,combined,fast-combined,leaf2,leaf8,leaf8+tiny-leaf,leaf8+combined,leaf8+fast-combined --rays 8192 --rounds 9 --out artifacts/bvh-full-comparison.json
```

该负对照包含已知错误的 `original`，工具会按实际校验失败设置非零退出码。复现 CPU0 配置还需在启动目录准备上述 `SwiftShader.ini`，并用 `taskset -c 0` 启动 CLI；结果的线程配置描述仍遵守第 4 节的观察范围。

恢复后的工作负载 CPU 烟测通过：`diagnostic` 与 `edges` 各 2,048 条 f32 输入的打包树结果与 f64 参考在状态和距离上全部一致；两个完整场景视角的缓存共享、射线格式和场景计数也已核验。完整的 `node --test tests/scene-bvh.test.mjs` 与 `npm run build` 也已通过。对应命令为：

```sh
node --test tests/scene-bvh.test.mjs
npm run build
```

上述检查属于 CPU 回归与应用构建，本轮物理 GPU 镜头验证配置数为 0。

生产路径中的变化集中于平行轴正确性修复；CPU 参考同步修复，新增回归测试。基准页面、工作负载、变体生成、结构证明与 CLI 位于实验 / 测试文件中，没有把任何未验证的微优化设为生产默认。
